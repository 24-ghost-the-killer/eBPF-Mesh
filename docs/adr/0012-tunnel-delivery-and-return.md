# 0012 Tunnel delivery and the return path

**Status:** Accepted (phase 3; approved by the project owner)

**Context.** Spec §5.1 step 10 tunnels clean packets to the customer's server
(outer IPv4, src = PoP unicast IP). §11.6 asks to support replies *through
the tunnel* as the default-safe option (many providers drop packets with a
foreign source, BCP38) and to document DSR. The spec does not say where the
origin should send replies when every PoP is anycast.

**Decision.**

*Forward.* Packets with an asset (`xs_tenants`, longest prefix) that pass the
policy are encapsulated in XDP: IPv4 in IPIP (protocol 4), IPv6 in 6in4
(protocol 41); outer src = PoP unicast IP, dst = asset origin, DF set,
TOS/traffic class copied (RFC 6040 normal mode), TTL 64. VLAN tags are kept;
the destination MAC is the configured next hop (or the frame's sender if none
is configured). Packets that would exceed the uplink MTU after the 20-byte
overhead are dropped as `drop_too_big` (ICMP "fragmentation needed" / "packet
too big" generation is deferred). The underlay is IPv4 only.

*Observe delivers.* Observe mode and the kill switch count verdicts but keep
delivering through the tunnel; only traffic without an asset goes to the PoP
kernel.

*Return.* One address of the anycast prefix is the tunnel endpoint
(`sentinelctl config set --tunnel-ep4`, lab: 198.51.100.1); it can never be an
asset. The customer script routes replies from the protected prefix into the
tunnel towards it (policy routing, NBMA `via <ep> onlink`). Anycast delivers
them to the PoP nearest the origin, so no per-origin PoP choice and automatic
failover. XDP accepts a return packet only if the outer header is plain (no
options, not fragmented), the inner source is an asset and the outer source
is that asset's registered origin (`drop_return` otherwise: a customer cannot
send through the platform with someone else's addresses). It clamps the MSS
of SYN/SYN-ACKs to MTU − 60 (IPv4) / MTU − 80 (IPv6), strips the outer header
and forwards to the next hop (`tx_return`).

*MSS.* The clamp handles an MSS that is the first option, optionally after up
to 4 NOPs (Linux, Windows and BSD stacks put it there); other orders pass
unchanged. A general option walk exceeded the verifier's 1M-instruction
budget (ADR 0013). It is defence in depth: the script sets tunnel MTU 1480,
so the origin's own route advertises a fitting MSS; with DSR the script sets
`advmss` on the reply route instead.

*Customer script.* Generated by `sentinelctl asset script` (later the API):
an `ipip`/`sit` device with no fixed remote (decapsulates from every PoP),
MTU 1480, protected prefix on `lo`, rp_filter off, policy routing for the
chosen return mode; idempotent `up`/`down`.

**Consequences.** Works behind BCP38 filtering by default. A customer that
spoofs return traffic is dropped at the PoP. A wrong customer MTU is rescued
for TCP by the clamp (tested). Large non-TCP packets above 1480 bytes are
dropped until ICMP generation lands.
